# Telemetry: what the planner reports, and what it does not

The planner sends an anonymous usage heartbeat to the API. This page is the complete
description of it. If something is not on this page, it is not collected.

## Why it exists at all

The server can only count what it stores, and it stores very little. A tab that has never
been synced lives entirely in your browser, and a signed-out user has no record on the
server of any kind. Between them that is most of the planner's use, so without a heartbeat
the only answerable question is "how many people made accounts", which is not the
interesting one.

What it is used for is deciding what to work on: whether anyone is on an old build before
a change is made that would break it, whether local plans or synced plans are the common
case, and roughly how large plans get.

## Exactly what is collected

One `POST /telemetry` on page load and one every five minutes after that. The body has
eight fields, one of them optional, and the server rejects it outright if it has any others:

| Field | What it is |
| --- | --- |
| `instanceId` | A random identifier for this browser. See below. |
| `signedIn` | Whether somebody is signed in. True or false, never who. |
| `tabCount` | How many planner tabs are open. |
| `localTabCount` | How many of those are local only. |
| `cloudTabCount` | How many of those are synced. |
| `factoriesTotal` | How many factories across all of those tabs. |
| `appVersion` | Which build of the planner is running. |
| `gitSha` | Which commit that build came from. Absent on builds that do not know, such as local ones. |

Counts, one flag and two build identifiers. That is the whole payload.

## The second endpoint: fault counts

There is one other thing the planner sends, `POST /events`, and it carries even less.

When the app corrects a broken plan on load, or shows you an error it had to admit defeat
over, it counts that. Once a minute, if and only if it has anything to report, it sends the
counts:

| Field | What it is |
| --- | --- |
| `instanceId` | The same random browser identifier as above |
| `appVersion`, `gitSha` | The same build identifiers as above |
| `events` | A list of `{ reason, count }` |

**`reason` is one of a fixed list written into the code.** The app cannot invent one, and the
server refuses anything not on the list. A reason is a short slug like
`plan_repair_export_orphaned`, and that is genuinely all it says.

**There is no message, no stack trace, no plan or factory name, and no identifier of any
kind beyond the browser id.** That is what makes it safe to send anonymously, and it is why
this is not error reporting: it can tell a maintainer that eleven plans needed the same
repair yesterday, and nothing whatsoever about whose.

Counts are kept in the server's memory and scraped away; nothing is written to the database.
Offline mode stops this too.

## What is not collected

No names of any kind: not your username, not plan names, not tab names, not factory names.
No account id, no email address, no token, no room id or invite link. No IP address is
stored (the request has one, as every request does, and nothing writes it down). No page
addresses, no clicks, no timings, no recipes, no plan contents. No error messages and no
stack traces. Nothing that is not in the two tables above.

## The instance id

It is a random UUID, generated by your browser, stored in `localStorage` under
`telemetryInstanceId`.

**It is not derived from your account and cannot be traced back to one.** It is not a hash
of a username, it is not seeded from an account id, and it is not taken from a session
token. It is minted before anyone signs in, and signing in or out does not change it, so
it carries nothing about who you are. The server keeps it only as a map key, so that one
browser heartbeating twelve times an hour counts as one browser rather than twelve.

Clearing your browser's site data deletes it, and the next visit mints a fresh one that
cannot be connected to the old one.

## How long it is kept

Fifteen minutes. A row that stops being updated is dropped entirely fifteen minutes after
its last heartbeat, both by an expiry index and by every read filtering on the timestamp.

It is stored in the database rather than in memory. That is a change from the first
version, which held it in memory only: the practical effect was that every deployment threw
the whole picture away, and the API deploys often. Nothing else about it changed, and the
fifteen minute limit is enforced the same way either way.

There is still no history. The metrics answer "how many right now"; nothing keeps
yesterday's answer.

## Turning it off

Offline mode stops it, along with every other request the planner makes. It is in the
account menu. A tracker blocker or an ad blocker also stops it, and the planner behaves
exactly the same when it is blocked, because nothing reads the response.

## For maintainers

The payload is defined once, in `common/src/schemas/telemetry.ts`, and both sides use that
definition. The schema rejects unknown fields rather than ignoring them, so a field added
by accident fails loudly instead of being quietly collected; the specs in
`common/src/schemas/telemetry.spec.ts` and `web/src/stores/telemetry-store.spec.ts` both
write the allowed field list out by hand, so adding one to the payload fails a test until
this page is updated too.

The metrics themselves are served at `GET /metrics` for Prometheus, behind a bearer token
in `METRICS_TOKEN`. See [deployment.md](./deployment.md) for setting that up.
